# OpenPulse AI v0.2 产品验证基线

## 1. 基线身份与状态

- `baselineVersion`: `0.1`
- `status`: `REVIEW_PENDING`
- 编写日期：`2026-09-10`
- 生效日期：`PENDING`
- Java / Platform 负责人评审：`PENDING`
- C++ Analyzer 负责人评审：`SssongZN`（2026-09-12T17:10+08:00）
- 来源任务：[第八步任务书](../tasks/08-v02-validation-baseline.md)

`REVIEW_PENDING` 表示样本、方法和门槛已经写入版本控制，但两位负责人尚未共同签字。签字前不得开始正式仓库运行、AI 对照或用户试用；签字后才把状态改为 `ACTIVE` 并填写生效日期。该状态不代表 H1 至 H4 已被证明。

## 2. 为什么现在先冻结基线

本基线遵循[产品方向 v0.2](../09-product-direction-v0.2.md)和[总体架构](../04-architecture.md)：先验证本地分析核心和透明报告是否有价值，再决定是否扩展 AI 或其他入口。样本只依据 GitHub 公开元数据、根目录结构、许可证和预设分层选择，没有运行或查看 OpenPulse 结果。

当前实现边界也决定了正式实验还不能立即开始：

- C++ analyzer 输出协议 `1.0`，统计文件、行数、语言和项目结构，只为缺少 README、LICENSE、CI 生成结构类发现；`quality` 仍是占位分数。
- C++ analyzer 当前把 `repository.path` 写成绝对路径。绝对路径属于敏感信息泄露检查项，不能通过归一化删除来掩盖。
- Java `AnalyzerReportReader` 只接受协议 `1.0`，检查顶层必填字段和每条发现的 `evidence`。
- Java `AnalyzerProcessRunner` 使用受限超时、退出码映射、临时目录以及清理逻辑，stdout 和 stderr 仅用于受限诊断，不属于可持久化报告。
- Java `AnalysisReportSnapshotFactory` 使用固定字段白名单；持久化快照只保存仓库名，不保存 `repository.path`，并拒绝绝对路径、凭据样式文本、越界相对路径和未批准证据字段。

这些是实验设计的输入，不是实验结果。报告协议 v2、CLI 分发和 Skill 必须由后续独立任务实现并验收。协议 `1.0` 没有修复方向字段，而且会把 `repository.path` 写成绝对路径，因此既不满足第 5.3 节的完整证据清单，也不满足第 10.1 节的零泄露门槛，不能用于正式运行。

## 3. 待验证假设

- **H1：确定性报告有独立价值。** 不使用 AI 时，用户仍能从终端摘要和 JSON 理解仓库事实、发现证据和下一步动作。
- **H2：相同输入产生稳定结果。** 分析器版本、规则版本、配置和仓库 commit 相同，且只应用第 6 节允许的归一化后，报告内容一致。
- **H3：OpenPulse-first 可能改善 AI 使用过程。** 与 AI 直接遍历相同仓库相比，先读 OpenPulse 摘要、再按需取证，可能减少输入 Token 或完成时间，同时不降低有效发现质量。
- **H4：新用户能够独立安装。** 非项目成员的 Windows x64 用户仅依据公开文档，可以安装、首次运行、理解错误和卸载 OpenPulse。

以上全部是假设，不得改写为产品事实或宣传数据。

## 4. 固定仓库样本

正式样本见 [repository-samples.csv](repository-samples.csv)，共 10 个：4 个 Java、4 个 C++、2 个其他语言对照。每个样本固定公开仓库 URL 和 40 位完整 commit SHA，不保存第三方源码。

### 4.1 选样规则

1. 先固定分层，再查看 GitHub 元数据，禁止查看 OpenPulse 输出后换样本。
2. GitHub 官方仓库页、commit 页面、根目录页面和该 commit 的许可证文件必须公开可访问。
3. GitHub 识别的许可证必须有明确 SPDX 标识；识别为 `NOASSERTION` 的候选不纳入本基线。
4. 排除私有仓库、归档或禁用仓库、恶意样本、已知真实凭据泄露样本和来源不明压缩包。
5. 样本不得全部来自同一组织、同一模板或同一个人。
6. 其他语言样本只验证仓库级事实，以及工具对不支持能力的诚实表达。

### 4.2 规模规则

规模使用 GitHub REST 仓库元数据的 `size` 值，单位为 KiB，只作为下载前的固定分层依据：

- `small`: `0` 至 `5,000` KiB。
- `medium`: `5,001` 至 `20,000` KiB。
- `near_limit`: `20,001` 至 `45,000` KiB。
- 大于 `45,000` KiB：本基线不选。

当前 Java 受控下载默认限制为压缩包 `50 MB`、解压后 `250 MB`、最多 `50,000` 个条目。GitHub `size` 不是压缩包或解压后大小的证明，因此正式运行仍必须让这些限制实际生效并记录受控失败；不得因某个固定样本触发限制而静默替换样本。

### 4.3 成熟度与结构缺口

- `mature`：锁定 commit 的仓库树中可见 README、许可证、测试和 CI，且项目维护结构较完整。
- `structure_gap`：在锁定 commit 的根目录预先确认至少缺少 CONTRIBUTING、CHANGELOG、CI 或明确测试目录中的一项。

当前分布为 7 个 `mature`、3 个 `structure_gap`。这里的判断来自锁定 commit 的 GitHub 仓库树，不是 OpenPulse 结果，也不预言分析器一定会生成某条发现。

## 5. 仓库运行实验

### 5.1 前置条件

只有以下条件全部满足才能填写 [repository-runs.csv](repository-runs.csv)：

1. 本基线由两位负责人评审并变为 `ACTIVE`。
2. 报告协议 `2.0` 已验收，且报告能明确记录协议版本、规则集版本和分析器版本；协议 `1.0` 不满足第 5.3 节的完整证据清单，也不满足第 10.1 节的零泄露门槛，因此不能用于正式运行。
3. Windows x64 CLI 的安装包版本、超时和大小限制已公开。
4. 报告默认不泄露绝对路径、疑似密钥、stdout、stderr 或异常堆栈。
5. 正式输出目录已被 `.gitignore` 或独立实验工作区隔离。当前 `.gitignore` 还没有覆盖报告输出（仓库根目录已存在未跟踪的 `report.json`），正式运行前必须另开范围明确的工程任务补上忽略规则。

### 5.2 固定步骤

1. 只获取 CSV 中锁定的 commit，并在运行前核对实际 SHA。
2. 记录操作系统版本、CPU 架构、安装包版本和公开配置，不记录用户名或个人绝对路径。
3. 对每个样本连续独立运行 3 次，每次使用新的输出目录。
4. 三次运行使用相同分析器版本、规则版本、配置、超时和资源限制。
5. 成功、部分成功、受控失败和超时都各保留一行（分类按第 5.3 节的 `run_outcome`）；不得只保留成功记录。
6. 原始报告留在受控实验工作区；公开仓库只提交必要统计、规范化哈希和脱敏短说明。

### 5.3 运行记录字段

CSV 表头：

```text
baseline_version,sample_id,run_number,commit_sha,analyzer_version,rule_set_version,report_protocol_version,started_at,duration_ms,timeout_ms,exit_code,run_outcome,failure_kind,report_status,report_bytes,normalized_hash,total_findings,complete_evidence_count,absolute_path_leak,suspected_secret_leak,stdout_leak,stderr_leak,stack_trace_leak,review_status,notes
```

字段分组：

- 身份字段：`baseline_version`、`sample_id`、`run_number`、`commit_sha`。
- 版本字段：`analyzer_version`、`rule_set_version`、`report_protocol_version`。
- 执行字段：`started_at`、`duration_ms`、`timeout_ms`、`exit_code`。
- 结果字段：`run_outcome`、`failure_kind`、`report_status`、`report_bytes`。
- 稳定与质量字段：`normalized_hash`、`total_findings`、`complete_evidence_count`。
- 安全字段：`absolute_path_leak`、`suspected_secret_leak`、`stdout_leak`、`stderr_leak`、`stack_trace_leak`。
- 复核字段：`review_status`、`notes`。

取值与判定：

- `run_outcome` 只能是 `COMPLETED`、`CONTROLLED_FAILURE`、`CRASH` 或 `HANG`。`COMPLETED`：进程按预期结束，报告状态为 `SUCCESS` 或 `PARTIAL_SUCCESS`。`CONTROLLED_FAILURE`：命中公开限制或预期错误路径（超时、大小限制、条目上限、路径不存在等），行为可解释且有明确错误输出。`CRASH`：非预期退出、崩溃或报告不可用。`HANG`：超过超时仍无响应，只能强制终止。第 10.1 节只接受 `COMPLETED` 和 `CONTROLLED_FAILURE`；出现 `CRASH` 或 `HANG` 直接触发第 11 节的返工条件。
- `failure_kind`：`run_outcome` 为 `COMPLETED` 时填 `NOT_APPLICABLE`，否则填具体类别，取值与平台已有的分析器失败枚举对齐：`TIMEOUT`、`START_FAILED`、`INVALID_ARGUMENTS`、`REPOSITORY_NOT_FOUND`、`SCAN_FAILED`、`REPORT_OUTPUT_FAILED`、`REPORT_MISSING`、`REPORT_INVALID`、`UNKNOWN_EXIT_CODE`、`OTHER`。
- `timeout_ms`：本次运行实际使用的超时，整数毫秒。
- `report_protocol_version`、`report_status`、`exit_code`、`report_bytes`：分别记录报告声明的协议版本、报告中的 `status`（`SUCCESS`、`PARTIAL_SUCCESS`、`FAILED`）、进程实际退出码和报告字节数；没有可用报告或无法取得时填 `NOT_AVAILABLE`。
- `review_status`：`` 表示该行尚未复核，`REVIEWED` 表示已按第 7 节完成复核。
- `total_findings`：报告中发现的全部条数。`complete_evidence_count`：其中满足下面"完整证据清单"的条数。
- 完整证据清单（每条发现必须全部满足；缺任意一项就不计入分子，并在 `notes` 写出缺失的字段名）：
  1. `ruleId` 非空，且属于该次运行记录的 `rule_set_version`。
  2. `type` 是第 7.1 节定义的规则类型之一。
  3. 位置：文件级发现必须有仓库内相对路径且 `startLine ≥ 1`；仓库级发现必须显式标记为仓库级，位置字段可以为空，并按"位置不适用"计入完整。
  4. `evidence` 非空，且字段都在已批准清单内。
  5. 修复方向非空。
- 第 3 项和第 5 项需要报告协议 `2.0` 提供仓库级标记和修复方向字段（暂定名 `scope` 与 `remediation`）。字段名以报告协议 v2 任务的验收结果为准；本清单只要求语义等价，改名不构成基线实质变化，但必须记录在第 14 节。
- 泄露判定：对本次运行产生的报告，以及将被记录或提交的摘要，做同一次统一扫描。五个安全字段的取值只能是 `YES`、`NO` 或 `NOT_AVAILABLE`；没有报告或没有可扫描内容时填 `NOT_AVAILABLE`，不得用 `NO` 冒充"未检查"。
  - `absolute_path_leak`：出现盘符路径、UNC 路径或以 `/` 开头的绝对路径。
  - `suspected_secret_leak`：出现 token、私钥或 `Bearer` 样式凭据文本。
  - `stdout_leak`、`stderr_leak`：报告或被记录的摘要中出现分析器进程 stdout 或 stderr 的内容。
  - `stack_trace_leak`：出现异常堆栈样式文本。

时间使用带时区 ISO 8601，耗时使用整数毫秒。失败行无法产生的字段填写 `NOT_AVAILABLE`，不能填写 `0` 冒充测量值。

## 6. 规范化与稳定性比较

“规范化”只消除明确的运行时差异，不改变发现内容。固定算法如下：

1. 以 JSON 解析器读取报告；解析失败直接记为失败，不参与伪造哈希。
2. 只移除顶层 `taskId`、`generatedAt`，以及未来协议明确声明的运行耗时字段。
3. JSON 对象键按 Unicode 码点升序输出，使用 UTF-8、无多余空白的规范 JSON。
4. 数组保持原顺序。只有报告协议明确把某个数组声明为无序集合后，才能按该协议指定的稳定键排序；当前协议 `1.0` 没有此声明。
5. 不删除或改写 `repository.path`、规则结果、相对路径、统计数、证据、消息、状态、协议版本或质量字段。
6. 对规范 JSON 字节计算 SHA-256，写入 `normalized_hash`。

同一样本 3 次的规范化哈希必须完全相同。若要改变以上规则，必须提升 `baselineVersion`，说明原因，并保留旧数据的原解释。

## 7. 人工复核方法

### 7.1 复核单位与字段

逐条复核记录写入 [finding-reviews.csv](finding-reviews.csv)。一条不同发现由 `sampleId + commitSha + ruleId + 相对文件路径 + 位置 + 规范化证据` 唯一标识，并写入 `finding_id`。每条发现至少由一人检查锁定 commit 的对应证据，每次复核单独占一行，并记录：

- `sampleId`、`commitSha`、`ruleId`、相对文件路径和位置。
- 规则类型：`PROJECT_STRUCTURE`、`TEXT` 或 `SYNTAX_TREE`。`PROJECT_STRUCTURE` 沿用协议 `1.0` 的 `type` 取值；`TEXT` 和 `SYNTAX_TREE` 由协议 `2.0` 新增。
- 结论：`CONFIRMED`、`FALSE_POSITIVE`、`UNCERTAIN` 或 `NOT_APPLICABLE`。
- `actionable`：用户能否指出下一步检查或修改动作。
- 一句不含源码和敏感信息的依据、匿名复核人编号、带时区复核时间。

CSV 表头：

```text
baseline_version,finding_id,review_row_id,sample_id,commit_sha,rule_id,relative_path,start_line,end_line,start_column,end_column,evidence_fingerprint,rule_type,review_stage,reviewer_id,blinded,verdict,actionable,rationale,reviewed_at,final_verdict,final_actionable,disagreement_resolution,notes
```

一行只属于一位复核者，任何一行都不包含另一位复核者的结论，因此第二位复核者不会在同一行里看到第一份判断：

- `review_row_id` 每行唯一，`reviewer_id` 是匿名编号，不是真实身份。
- `review_stage` 为 `INDEPENDENT` 的行只填 `verdict`、`actionable`、`rationale`、`reviewed_at`，`final_verdict`、`final_actionable` 和 `disagreement_resolution` 留空；该行必须满足 `blinded = YES`，表示填写时没有查看同一发现的其他复核行。填 `NO` 的行不算独立复核。
- 普通发现只需要一人独立复核；影响 Java/C++ 共同协议、存在争议或首位复核者选择 `UNCERTAIN` 的发现必须有两行 `INDEPENDENT` 记录，且第二行要在第二人完成自己的判断之后才写入。
- 最终结论单独占一行：`review_stage` 填 `FINAL`，只填 `final_verdict`、`final_actionable`、`disagreement_resolution` 和 `notes`，`reviewer_id` 填 `BOTH`（两人一致）或 `ARBITER`（分歧后由两人共同裁定）。所需复核没有完成前不得出现 `FINAL` 行。
- `evidence_fingerprint`：对该发现的规范化证据计算 SHA-256，不保存源码正文；规范化口径与第 6 节一致，只对证据对象本身做键排序和紧凑输出。

保留两人的原判断和最终决定，不覆盖分歧记录；两人判断不一致时 `disagreement_resolution` 必须填写。

### 7.2 指标

- 准确率只使用最终结论计算：`precision = final_verdict 为 CONFIRMED 的行数 / (final_verdict 为 CONFIRMED 的行数 + final_verdict 为 FALSE_POSITIVE 的行数)`。
- `final_verdict` 为 `UNCERTAIN` 或 `NOT_APPLICABLE` 的行不进入准确率分母，但必须分别报告数量。
- 可行动率只使用最终字段计算：`actionable_rate = final_verdict 为 CONFIRMED 且 final_actionable 为 YES 的行数 / final_verdict 为 CONFIRMED 的行数`。
- 证据完整率 `evidence_completeness = complete_evidence_count / total_findings`；两个字段和"完整证据清单"的判定见第 5.3 节。

以上指标只使用 `review_stage` 为 `FINAL` 的行，并按 `finding_id` 去重；`INDEPENDENT` 行用于保留两位复核者的原始判断，以及统计分歧和独立复核数量。

若准确率分母为 0，则填写 `NOT_AVAILABLE`，不得写为 0% 或 100%。人工判断必须来自仓库证据，AI 输出不能作为正确答案。

## 8. AI 公平对照条件

本任务只冻结协议和 [ai-comparisons.csv](ai-comparisons.csv) 表头，不调用 AI。正式对照必须等报告协议、CLI 和 Codex Skill 各自验收后进行。

### 8.1 共同条件

- 使用同一个明确模型版本、相同推理设置、相同锁定 commit、相同审查提示词版本和相同完成标准。
- 每次从没有仓库历史的新对话开始，不复用回答或人工追加提示。
- 明确记录 AI 是否可访问仓库文件、OpenPulse 报告和证据片段：`repository_access`、`openpulse_report_provided`、`evidence_snippets_provided` 各自填 `YES` 或 `NO`；`mode` 只是分组标签，不能代替这三个字段。
- 记录所用工具链版本：`cli_version`、`skill_version`（对照组填 `NOT_APPLICABLE`）、`analyzer_version`、`rule_set_version` 和 `report_protocol_version`，保证两组可复现。
- 在至少 3 个代表仓库上，每种模式独立运行 2 次；同一个 `pair_id` 只配对同一样本、提示词、模型设置和运行序号。
- Token 只记录 API 或工具实际给出的数值；不可得时填写 `NOT_AVAILABLE`，不能估算或写 0。
- `unsupported_claims`：AI 输出中给出了断言，但没有任何仓库证据或 OpenPulse 证据支撑的条数；逐条把 AI 断言与证据对照，无法对应的计为 1 条。
- `confirmed_findings`、`false_positives`、`uncertain_findings` 是 AI 输出经第 7 节人工复核后得到的计数；把依据的复核行写进 `review_refs`（分号分隔），保证能回溯到 `finding-reviews.csv`。AI 的断言不是规则命中时，其在 `finding-reviews.csv` 中的 `rule_id` 和 `rule_type` 填 `NOT_APPLICABLE`。

### 8.2 对照组与实验组

- `CONTROL`：AI + 仓库访问 + 固定审查提示词；不提供 OpenPulse 报告，也不暗示预期问题。
- `OPENPULSE_FIRST`：AI + 仓库访问 + 同一提示词 + 已验收 Skill + 同一 commit 的 OpenPulse 报告；先读摘要、再按需取证，证据不足时允许读取必要源文件。

两组都允许为验证结论读取源文件，并记录 `source_file_reads`。不得为了让 Token 数更好看而禁止实验组核对证据。两组输出均按第 7 节由人工复核，只保存统计和脱敏短摘要，不提交完整对话或源码。

## 9. Windows x64 安装试用

本任务只提供空白的 [user-trial-template.md](user-trial-template.md)，不邀请或代填正式试用者。

正式试用需至少 3 名非项目成员、未参与安装脚本开发的 Windows x64 用户，并事先告知记录范围和删除权：

1. 试用者只阅读公开安装文档。
2. 从拿到公开发布包开始计时。
3. 在其有权使用的本地仓库运行分析。
4. 找到终端摘要和 JSON 报告。
5. 解释至少一条发现的证据和下一步动作。
6. 执行卸载，或准确指出全部安装内容的位置。

项目成员只要提供文档外命令、远程操作或文件修改，该次必须标记 `needs_project_help: YES`，不能算独立安装成功。模板只记录匿名编号、系统版本和架构、带时区时间、耗时、各阶段成败、原始错误类别和用户自己的简短反馈，不记录姓名、账号、联系方式或个人绝对路径。

模板还必须记录资格与常见 Windows 失败模式：`is_project_member` 和 `participated_in_installer_development` 都必须为 `NO`，任一不是 `NO` 的试用不计入第 10.2 节；另记录缺少运行库或 DLL、PATH 未生效、权限不足、杀毒或 SmartScreen 拦截，并以“原始错误类别”作为兜底。

## 10. 成功门槛

这些门槛只用于小样本工程决策，不用于市场宣传。

### 10.1 核心分析门槛

- 10 个样本都在公开限制时间内结束。第 5.3 节的 `run_outcome` 只接受 `COMPLETED` 和 `CONTROLLED_FAILURE`；不允许 `CRASH` 或 `HANG`。
- 30 次运行中，每个样本的 3 个规范化哈希完全一致。
- 每条发现都有完整规则编号、类型、相对位置、证据和修复方向，证据完整率为 100%（"完整"按第 5.3 节的完整证据清单逐条判定；`total_findings` 为 0 时填 `NOT_AVAILABLE`，不得写成 100%）。
- 第 5.3 节的五个安全字段全部为 `NO`；出现 `YES` 即不通过，填 `NOT_AVAILABLE` 也不算通过。
- 人工复核准确率至少 80%，并单独公开 `UNCERTAIN` 数量。
- 至少 5 个样本各产生至少一条 `CONFIRMED` 且 `actionable` 的发现。

### 10.2 安装门槛

- 至少 2/3 试用者在 10 分钟内完成首次分析。
- 至少 2/3 试用者不需要项目成员提供文档以外帮助。
- 3/3 试用者完成卸载，或准确知道全部安装内容的位置。

### 10.3 AI 辅助门槛

- 实验组 `CONFIRMED` 发现数的中位数不低于对照组。中位数取该模式全部有效运行（至少 3 个代表仓库 × 各 2 次）的 `confirmed_findings` 值；`completed` 为 `NO` 的运行不参与计算并在 `notes` 说明。
- 实验组的误报数和无依据断言数均不高于对照组，比较口径同为上述中位数。
- 至少 2/3 代表仓库上，实验组输入 Token 降低至少 20%，或完成时间降低至少 20%。每个代表仓库取该模式 2 次运行的 `input_tokens`（或 `duration_ms`）中位数，实验组相对对照组下降不少于 20% 的仓库数必须不少于 2/3（即至少 3 个代表仓库中的 2 个）。
- Token 不可得时不得宣称节省 Token，只依据实际耗时和质量判断。

## 11. 继续、返工和停止条件

- **继续报告协议与 CLI 工作**：仅当本基线由两位负责人完成评审，样本和门槛没有未解决的 Java/C++ 边界分歧。
- **先返工分析核心**：任一样本结果不稳定、崩溃、无限等待、泄露敏感信息、证据不完整、准确率低于 80%，或大部分样本只有低价值结构统计。
- **停止 Skill 和 MCP 扩展**：核心分析门槛未通过时不得开始；AI 辅助门槛未通过时保留本地 CLI，但不开发 MCP，也不宣传减少 Token。
- **停止把独立安装作为已验证能力**：安装门槛未通过时先修订发布包和公开文档，再用新试用者重新验证，不得把获得口头帮助的结果算作成功。
- **重新评审产品入口**：若真实试用证据主要指向 PR 自动检查、历史对比或团队共享，只能在 GitHub Action、MCP、团队网站中重新选择一个方向，不能同时启动。

任何固定样本、公式、门槛、归一化规则或公平条件的实质变化都必须提升基线版本；旧记录继续按旧版本解释，不覆盖、不删除失败数据。

## 12. 数据与安全规则

- 不提交第三方源码、压缩包、构建产物、完整报告工作区或完整 AI 对话。
- 不记录 Token、Cookie、Authorization Header、真实姓名、联系方式、用户名或个人绝对路径。
- 疑似密钥只记录规则 ID、相对位置和脱敏类型，不保存原文。
- CSV 使用 UTF-8、英文逗号和一行表头；含逗号、换行或双引号的值必须按标准 CSV 双引号转义。
- 正式结果必须保留失败行，且每行带 `baseline_version`。
