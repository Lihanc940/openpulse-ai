# OpenPulse AI 第十四步：Windows x64 CLI 分发基线

## 任务定位

- 建议分支：`feat/analyzer-windows-distribution`
- 负责人：C++ Analyzer 负责人
- 前置任务：任务 12 已由 PR #28 合并到 `main`（`5c63638`）
- 可并行任务：`13-java-analyzer-runtime-v2.md`
- 任务性质：把现有 C++ Analyzer 做成可复现、可校验、可安装和可卸载的 Windows x64 CLI 包

本任务不增加扫描规则，也不切换 C++ 默认协议。它为显式 v2 增加安全、简短的人类终端摘要，并建立 Windows x64 分发边界，让没有 Visual Studio 和 CMake 的试用者能够从一个固定版本压缩包运行分析、阅读结果概览、核对文件完整性、理解依赖、升级和卸载。

本任务先完成“可分发工程基线”，不在 Git 仓库提交 exe/zip，也不直接发布 GitHub Release。正式公开发布还必须先由两位负责人共同确定项目许可证。

## 为什么单独做这一步

当前源码可以在开发机编译，但“开发者能编译”不等于“普通用户能安装”。真实产品至少要回答：

- 用户下载哪个文件，如何确认没有损坏。
- 是否需要额外 Visual C++ 运行库。
- 程序、许可证和第三方声明如何一起交付。
- 路径含空格时能否运行。
- 如何升级、回退和完全卸载。
- 输出文件放在哪里，失败后是否留下半成品。

如果这些问题没有固定，后续 H4 安装试用和 Codex Skill 都无法复现。

## 本步骤需要理解的名词

- **分发包**：交给用户运行的压缩包，包含程序和必要说明，不等同于源码目录。
- **可复现构建**：相同源码、工具链和配置能得到内容边界一致、来源可追踪的产物。
- **运行时依赖**：程序启动时仍需要的 DLL 或系统组件。
- **静态/动态运行库**：依赖是否编入程序，或由系统 DLL 在运行时提供；必须根据实际构建验证，不能猜。
- **SHA-256 校验文件**：用户可用来确认下载文件没有损坏或被替换的摘要。
- **第三方声明**：列出打包软件使用的第三方代码、版本、来源和许可证。
- **安装**：把版本化目录放到约定位置，并让用户可以稳定调用。
- **升级**：安装新版本且不覆盖用户报告，旧版本可以回退。
- **卸载**：删除程序和由安装步骤创建的入口，不删除用户仓库或报告。
- **冒烟测试**：使用打包后的程序完成最小真实运行，确认压缩、解压和依赖没有破坏程序。
- **终端摘要**：从已经生成的结构化报告提取少量固定字段供人阅读；JSON 仍是完整事实来源。
- **有界输出**：限制终端条目数和单项长度，避免大型仓库把控制台或 AI 上下文塞满。
- **构建产物污染**：把本机 exe、缓存、临时报告或绝对路径误提交到 Git。

本任务不得擅自替项目选择 MIT、Apache-2.0 或其他许可证。若负责人尚未决定，验收报告标记“本地分发基线完成，公开发布被许可证决定阻塞”，不能伪装成已发布。

## 分发包边界

建议本地包名使用：

```text
openpulse-analyzer-<version>-windows-x64.zip
```

压缩包内部至少包括：

```text
openpulse-analyzer-<version>/
  bin/
    openpulse-analyzer.exe
  README.txt 或 README.md
  THIRD_PARTY_NOTICES.md
  LICENSE（仅在项目许可证已由双方确定后加入）
```

要求：

- 版本来自 CMake 项目版本，不在脚本中另写一份。
- 架构固定标记为 `windows-x64`，不把本机 CPU 名称直接拼入。
- 包内不含源码、fixture、构建目录、PDB、测试程序和临时报告，除非后续调试包单独设计。
- ZIP 外生成 `<zip>.sha256`，格式固定并有自动校验测试。
- 压缩包文件清单和顺序稳定；时间戳若无法稳定，必须说明规范化边界，不能虚称逐字节可复现。
- 第三方声明至少覆盖实际进入或影响产物的 `nlohmann/json` 与 `picosha2`，记录版本/提交、来源和许可证。

## 构建和依赖要求

- 使用 Release 配置和 x64 架构。
- 记录 CMake、生成器、MSVC、Windows SDK 和架构。
- 明确使用动态还是静态 MSVC 运行库，并在干净环境或依赖检查工具中验证。
- 构建过程必须从仓库根或脚本位置可靠解析路径，不依赖当前工作目录。
- 构建、测试和组包失败立即停止，不产生看似完整的旧 ZIP。
- 网络依赖必须锁定版本；无法下载时给出明确错误，不从开发者未知缓存悄悄取代来源。
- 所有临时目录位于系统临时目录或被忽略的构建目录，结束后按成功/失败策略清理。

如果采用 CPack，应建立明确的 `install()` 规则并测试安装树；如果采用 PowerShell 组包，脚本只能编排已构建产物，不能复制一份产品逻辑。

## 用户运行入口

分发文档必须把协议写明确：

```powershell
.\openpulse-analyzer.exe --protocol 2.0 --path <repository> --output <report.json>
```

要求：

- 当前正式 v0.2 验证只允许显式 `--protocol 2.0`。
- 无参数默认仍是 v1；不得在本任务切换默认值。
- 文档同时说明 `--protocol 1.0` 只用于兼容旧调用方，v1 含绝对路径且不能用于正式实验。
- `--help`、未知参数、缺少值、路径含空格和输出路径含空格必须在打包后程序上真实验证。
- 成功时报告写入用户指定位置；失败时不得留下被误认为完整报告的文件。

## 人类终端摘要

新增明确的摘要参数，建议为：

```powershell
.\openpulse-analyzer.exe --protocol 2.0 --summary --path <repository> --output <report.json>
```

具体参数名可以按现有 CLI 风格调整，但行为必须满足：

- 只有调用方显式要求时才输出摘要；Java 当前不会传该参数。
- 首版摘要只支持协议 `2.0`。与 `1.0` 同时使用时返回安全的参数错误，不读取 v1 的占位健康分。
- JSON 文件仍是完整、机器可读的事实来源；摘要不得建立第二套扫描或规则判断。
- 摘要从本次已经构造并验证的 v2 报告或同一内存模型生成，不能重新扫描仓库。
- 至少显示 Analyzer/Rule set 版本、报告状态、可复核性、文件数、语言数、发现数、限制数。
- 每条展示的发现只包含 `ruleId`、严重程度、作用域和简短修复方向；文件级规则未来只能显示安全相对路径。
- 发现和限制条目必须有固定上限；超出时显示“还有多少条未展示”，不能无限打印。
- 不显示输入目录、输出文件绝对路径、源码、evidence 正文、用户名、凭据样式、stdout/stderr 或堆栈。
- 输出顺序与 v2 报告稳定顺序一致；同一规范化报告产生相同摘要。
- `SUCCESS`、`PARTIAL_SUCCESS` 和可安全生成的 `FAILED` 摘要含义明确，终端摘要不能覆盖真实进程退出码。
- 默认不传 `--summary` 时保留现有脚本和 Java 所依赖的行为。

建议把摘要格式化放进独立小组件或函数，并用内存中的受约束模型作为输入。不要在 `main.cpp` 里手写另一套规则目录，也不要用正则从 JSON 字符串截取字段。

## 安装、升级、回退和卸载

本任务可以选择“免安装 ZIP”作为首个分发方式，但必须明确流程：

- 安装：解压到用户选择的版本化目录；首版不强制修改系统 PATH。
- 运行：从 `bin` 目录显式调用，或由用户自行添加用户级 PATH。
- 升级：新版本解压到新目录，不覆盖旧版本和报告。
- 回退：重新使用旧版本目录，并明确报告协议选择。
- 卸载：删除对应版本目录和用户自行创建的 PATH 项；不删除仓库、输出报告或其他版本。

脚本不得静默修改系统级 PATH、注册表执行策略或管理员权限设置。若提供可选的用户级 PATH 辅助脚本，必须支持撤销并在执行前说明改动。

## 安全要求

- 打包脚本不读取或打包 `.env`、Git 凭据、SSH 密钥和用户目录。
- 文档和产物清单不出现用户名、绝对工作区路径或代理地址。
- 打包后 v2 报告继续通过任务 12 的绝对路径、凭据、stdout、stderr 和堆栈扫描。
- 构建日志可以留在本机临时目录，但不能进入分发包。
- 不使用未校验的下载 URL 或 `Invoke-Expression` 执行远程脚本。
- SHA-256 用于完整性校验，不宣传为代码签名；首版没有签名就如实说明。

## 自动化测试要求

至少覆盖：

1. Release x64 配置、编译和完整 CTest 通过。
2. 从干净临时目录执行 install/组包流程。
3. ZIP 文件名、根目录和允许文件清单正确。
4. 包内没有源码、测试二进制、PDB、缓存、个人路径和报告。
5. SHA-256 文件可以重新计算并匹配。
6. 解压后的 `openpulse-analyzer.exe --help` 返回 `0`。
7. 打包程序默认 v1 回归仍通过。
8. 打包程序显式 `--protocol 1.0` 通过。
9. 打包程序显式 `--protocol 2.0` 生成合法报告。
10. 显式 v2 摘要包含固定概览和有界发现，不包含绝对路径、源码、凭据或进程诊断。
11. v1 与摘要参数组合被安全拒绝；不传摘要参数时行为保持兼容。
12. 路径和输出文件名包含空格时通过。
13. 未知协议、缺少值、仓库不存在和输出失败使用既定退出码。
14. 打包程序生成的 v2 报告通过正式 Schema 和 Java 联合 Reader。
15. 同一 fixture 两次运行的规范化哈希和终端摘要均一致。
16. 运行时依赖检查与文档描述一致。
17. `git status` 不出现 exe、zip、报告或构建缓存。

## 验证入口

建立一个可从仓库根运行的明确脚本，例如：

```powershell
.\scripts\build-windows-x64-package.ps1
.\scripts\verify-windows-x64-package.ps1 -PackagePath <zip>
```

具体名称可以按现有脚本风格调整，但构建与验收职责应分开。验收报告必须记录：

- 源 commit、Analyzer 版本和 Rule set 版本
- CMake、生成器、MSVC、Windows SDK 和架构
- CTest 数量和结果
- 包名、文件清单、字节数和 SHA-256
- 运行时依赖结论
- v1/v2/错误路径冒烟结果
- 终端摘要正常、部分成功、失败、有界和零泄露结果
- Schema、Java Reader 和输出安全结果

## 明确不做

- 不切换默认协议。
- 不删除或弃用 v1。
- 不修改 Java、数据库、HTTP API、Vue 或协议 Schema。
- 不新增分析规则、Tree-sitter、健康评分或 AI 总结。
- 不实现 Codex Skill、MCP、GitHub Action 或自动更新。
- 不创建网站下载页。
- 不提交或发布二进制产物。
- 不在未决定项目许可证时创建公开 GitHub Release。
- 不填写正式仓库实验或用户试用结果。

## 完成标准

1. Windows x64 Release 包可以通过单一入口可复现地构建和验收。
2. 没有开发工具的目标用户能够依据文档理解解压、运行、升级、回退和卸载。
3. 包名、内容、版本、SHA-256、第三方声明和运行时依赖准确。
4. 显式 v2 能输出安全、有界、稳定的人类摘要，且 JSON 保持唯一完整事实来源。
5. 打包后的真实程序通过 v1/v2、错误路径、确定性和输出安全验证。
6. 默认协议仍为 v1，正式文档只用显式 v2 运行正式验证。
7. 仓库不包含二进制、缓存、报告或个人环境信息。
8. 若根级许可证尚未决定，明确阻塞公开发布，不伪造“可公开发布”。
9. `git diff --check` 通过，改动只在允许范围。
10. 创建一个范围单一的本地 commit，不 push、不创建 PR，先回主线验收。
