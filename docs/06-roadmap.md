# OpenPulse AI 交付路线图

路线按“验收门槛”推进，不按赶进度推进。当前阶段没有达到完成标准，就不把复杂功能叠上去。

> 2026-09-02 更新：路线已从“网站优先的 AI 仓库分析平台”调整为“本地分析核心优先，人和 AI 复用同一透明报告”。变更原因和范围见 `docs/09-product-direction-v0.2.md`。

## P0：工程基线

目标：两个人对产品边界、架构和协作方式形成同一理解。

完成标准：

- GitHub 仓库建立，`main` 受保护
- Java、C++、Web 和文档目录清晰
- JSON 协议及示例可共同评审
- 提交、分支、PR 和完成定义明确

## P1：本地最小闭环

目标：不依赖 GitHub、数据库和 AI，先证明 Java 与 C++ 能可靠协作。

完成标准：

- Java 提供健康检查和创建分析任务接口
- C++ 能扫描一个本地示例目录并输出合法 JSON
- Java 能启动 C++、处理超时和退出码、解析报告
- 正常与失败路径都有自动化测试

## P2：真实 GitHub 仓库分析

目标：用户输入公开仓库 URL 后得到可追踪的分析任务。

完成标准：

- 安全解析 GitHub URL 并获取基础信息
- 受控下载仓库，限制大小、时间和目录
- MySQL 保存项目、任务、状态和报告
- 失败可以定位，临时文件能够清理

P2 已完成 URL、元数据和受控下载；任务与报告持久化实现已提交 PR #16。PR 完成评审后冻结该方向的新功能，先进入产品价值验证。

## P3：本地产品与透明报告

目标：新用户无需网站和 AI，也能在本地得到稳定、可理解的仓库报告。

完成标准：

- Windows x64 本地 CLI 有明确安装、升级、卸载和运行方法
- CLI 同时提供便于人阅读的终端摘要和机器可读 JSON
- 第一批规则有固定编号、严重等级、证据、修复方向和测试样例
- 同一版本分析器对同一代码产生稳定结果
- 报告包含分析器版本和规则版本
- 报告协议升级有兼容策略，不破坏现有 v1 调用方
- 不显示未经真实数据验证的总健康分

## P4：一个 Skill 与真实价值验证

目标：证明 AI 读取 OpenPulse 报告，相比直接读取仓库具有可测量价值。

完成标准：

- 先只发布一个可复现的 Codex Skill 适配，不承诺 Skill 格式跨 AI 通用
- 至少选择 10 个规模和语言不同的真实仓库运行分析
- 比较 AI 直接阅读与 OpenPulse 辅助两种方式的输入 Token、耗时、确认有效的发现和重复运行稳定性
- 至少邀请 3 名非项目成员试用，并记录是否能独立安装和理解报告
- 未经测量，不宣传节省 Token、提高准确率或支持深度多语言分析

## P5：按验证结果选择一个扩展入口

目标：只根据真实反馈选择下一种使用方式，不同时扩展所有入口。

候选方向：

- MCP：让支持 MCP 的 AI 按需调用分析和证据查询
- GitHub Action：在 CI 或 Pull Request 中运行确定性检查
- Java + Vue 团队模式：保存历史报告、项目对比和多人查看

进入标准：

- P4 的试用记录明确出现相应需求
- 新入口只调用既有分析核心，不复制规则
- 安全、安装成本和维护责任有明确验收标准

## P6：v0.2 公开发布

目标：形成可安装、可理解、可反馈的开源版本。

完成标准：

- 许可证、贡献指南、版本说明齐全
- 示例仓库演示稳定
- 已知限制公开
- 发布 `v0.2.0`，后续需求进入 Issue 管理
- 公开当前支持的语言、规则能力和已知限制
- 网站、AI、MCP 和私有仓库能力只描述已经验证和交付的部分
