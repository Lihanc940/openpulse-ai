# OpenPulse AI 交付路线图

路线按“验收门槛”推进，不按赶进度推进。当前阶段没有达到完成标准，就不把复杂功能叠上去。

## P0：工程基线

目标：两个人对产品边界、架构和协作方式形成同一理解。

完成标准：

- GitHub 仓库建立，`main` 受保护
- Java、C++、Web 和文档目录清晰
- JSON 协议及示例可共同评审
- 提交、分支、PR 和完成定义明确

## P1：本地最小闭环

目标：不依赖 GitHub、数据库和 AI，先证明 Java 与 C++ 能可靠协作。

完成标准：

- Java 提供健康检查和创建分析任务接口
- C++ 能扫描一个本地示例目录并输出合法 JSON
- Java 能启动 C++、处理超时和退出码、解析报告
- 正常与失败路径都有自动化测试

## P2：真实 GitHub 仓库分析

目标：用户输入公开仓库 URL 后得到可追踪的分析任务。

完成标准：

- 安全解析 GitHub URL 并获取基础信息
- 受控下载仓库，限制大小、时间和目录
- MySQL 保存项目、任务、状态和报告
- 失败可以定位，临时文件能够清理

## P3：规则与健康评分

目标：报告稳定、结果可解释。

完成标准：

- 第一批规则有固定编号、严重等级和测试样例
- 健康评分公式有文档和测试
- 同一版本分析器对同一代码产生稳定结果
- 报告协议升级有兼容策略

## P4：AI 项目顾问

目标：AI 基于结构化事实解释问题，不替代静态分析器猜测结果。

完成标准：

- Prompt 版本可追踪
- 输入只包含必要报告数据
- 输出有结构化格式和失败降级
- 成本、超时和敏感信息处理明确

## P5：前端、部署与持续集成

目标：普通用户可以稳定使用完整流程。

完成标准：

- Vue 页面覆盖提交、进度、报告和错误状态
- Docker Compose 一条命令启动依赖
- GitHub Actions 自动构建和测试 Java、C++、Web
- 新环境按 README 可以完成部署

## P6：公开发布

目标：形成可安装、可理解、可反馈的开源版本。

完成标准：

- 许可证、贡献指南、版本说明齐全
- 示例仓库演示稳定
- 已知限制公开
- 发布 `v0.1.0`，后续需求进入 Issue 管理
