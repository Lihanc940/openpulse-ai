# OpenPulse AI 产品方向 v0.2

## 决策信息

- 状态：团队已接受，合并到 `main` 后生效
- 日期：2026-09-02
- 类型：产品定位、架构优先级和交付路线调整
- 取代：`docs/01-mvp-v0.1.md` 中“网站 + 健康分 + AI 总结优先”的 MVP 路线

这是一份方向版本更新，不是已经发布的软件版本说明。它用于约束后续任务，避免在没有验证用户价值前同时建设 CLI、MCP、网站、AI、GitHub Action 和复杂评分。

## 一句话结论

OpenPulse AI 从“面向公开 GitHub 仓库的在线 AI 分析网站”调整为：

> 一个面向开发者和 AI 工具的本地优先仓库分析工具，先生成透明、可验证、可复现的结构化报告，再由人直接阅读或由 AI 按需解释。

网站、Java 团队服务和自动化入口继续保留为后续能力，但不再是本地分析成立的前置条件。

## 为什么调整

### 1. 通用代码审查市场已经成熟

SonarQube、GitHub CodeQL 和其他代码审查产品已经提供大量语言规则、安全检查和 Pull Request 集成。OpenPulse 不能只靠“输入仓库并让 AI 给建议”形成差异。

### 2. 当前分析能力需要如实定位

现有 C++ 分析器已经能够遍历目录、统计文件和行数、识别语言并检查 README、LICENSE、CI 等项目结构，但尚未形成多语言语义分析能力。

C++ 不是问题本身。后续可以接入 Tree-sitter 获得语法树，但每一种语言和规则都必须有真实测试，不能把文本搜索包装成深度静态分析。

### 3. 黑盒健康分缺乏可信依据

没有真实项目数据和相关性验证时，一个总分会制造不必要的精确感。v0.2 的核心输出改为透明发现：规则编号、严重程度、位置、证据和修复方向。

### 4. AI 应当解释事实，而不是制造事实

OpenPulse 首先在本地完成确定性分析。AI 只读取必要摘要和证据，帮助用户理解、排序和制定修改计划。即使用户不使用 AI，报告仍然完整可用。

### 5. 两人的工程基础可以继续复用

现有 Java/C++ 进程边界、超时和清理、GitHub 获取、协议解析及持久化不是废弃工作。它们分别支撑本地安全执行和后续团队模式，不需要为了方向调整而推倒重来。

## 目标用户与问题

第一验证阶段只面向两类用户：

1. 希望快速了解陌生仓库工程状态的个人开发者。
2. 希望给 AI 提供压缩、稳定仓库事实，而不是让 AI 每次重新遍历全部文件的 AI 编程工具用户。

暂不把大型企业、安全团队或需要完整漏洞检测的用户作为目标。OpenPulse 不与 SonarQube 或 CodeQL 比拼规则数量和安全研究深度。

## 产品核心与入口

```text
本地仓库或受控副本
        ↓
C++ Analyzer Core
        ↓
版本化结构化报告
        ├── 人直接阅读
        ├── 一个 AI Skill
        ├── 后续 MCP 工具
        ├── 后续 GitHub Action
        └── 后续 Java + MySQL + Vue 团队模式
```

只有 C++ Analyzer Core 负责产生分析事实。所有入口都必须复用同一报告协议和规则实现。

## v0.2 第一验证阶段

### 必须完成

- 第一分发平台限定为 Windows x64，并提供可安装和卸载的本地 CLI。
- CLI 同时提供便于人阅读的终端摘要和机器可读 JSON。
- 对本地仓库路径进行安全、有边界的扫描。
- 报告携带分析器版本和规则版本。
- 每条发现包含规则编号、严重程度、位置、证据和修复方向。
- 第一批规则有自动化测试和公开限制说明。
- 一个 Codex Skill 能运行分析器、先读摘要、再按需读取证据。
- 如果增加语法树规则，v0.2 先限定 Java 和 C++；其他语言只输出已验证的仓库级事实。
- 至少在 10 个真实仓库上记录结果。
- 至少邀请 3 名非项目成员尝试安装和使用。

### 明确不做

- 不调用 AI API 生成平台自有总结。
- 不发布未经验证的总健康分。
- 不同时开发 MCP、GitHub Action、Vue 网站和团队部署。
- 不承诺全面多语言 AST 或完整安全漏洞检测。
- 不实现自动修改代码或自动提交 Pull Request。
- 不引入 Redis、消息队列、微服务或大规模并发扫描。

## 使用逻辑

### 人直接使用

```text
安装 OpenPulse -> 选择本地仓库 -> 生成报告 -> 查看发现和证据
```

该流程必须在没有账号、网站和 AI 的情况下成立。

### Codex Skill 使用

```text
用户要求 AI 检查项目
-> Skill 调用本地分析器
-> AI 先读取报告摘要
-> AI 只在需要时查询某条发现的证据
-> AI 解释原因并提出修改步骤
```

AI 接收到的工具输出仍可能进入模型上下文，因此必须限制绝对路径、源码片段和疑似密钥。默认报告应尽量使用相对路径，证据正文按需返回。

Skill 格式和安装方式可能因 AI 产品而异。第一阶段只保证 Codex 适配可复现，不把同一个 Skill 包宣传为所有 AI 产品都能直接安装。跨工具入口优先在后续评估 MCP。

### 后续团队模式

```text
用户提交 GitHub 地址
-> Java 受控下载并创建任务
-> 调用同一 C++ 分析器
-> MySQL 保存报告历史
-> Web 展示项目对比和团队结果
```

团队模式只有在用户明确需要历史、共享或自动分析时才继续建设。

## 验证方法

### 分析质量

- 对同一提交重复运行，比较报告是否稳定。
- 人工复核每条规则的有效发现和明显误报。
- 分开记录项目结构规则、文本规则和语法树规则，不能混称。

### AI 使用价值

对同一仓库执行两组实验：

1. AI 直接阅读仓库。
2. AI 先读取 OpenPulse 摘要，再按需读取证据。

记录输入 Token、完成时间、确认有效的发现数量、误报数量和重复运行差异。在实验完成前，只能把“减少 Token、提高稳定性”写成待验证假设，不能写成产品事实。

### 安装体验

- 记录新用户从下载到第一份报告所需时间。
- 记录缺少运行库、PATH、权限和跨平台构建问题。
- 安装失败必须有明确错误和卸载方法。

## 两人职责

### C++ 负责人

- 本地分析核心、CLI 和跨平台构建。
- 文件与语言识别、Tree-sitter 接入和规则执行。
- 报告生成、性能边界和分析器测试。

### Java 负责人

- 分析器进程安全、报告解析和兼容性。
- 后续 MCP 适配、GitHub 编排、持久化和团队 API。
- 验证数据整理、安全输出边界和安装流程支持。

### 共同负责

- 报告协议和规则定义。
- Codex Skill 使用规范。
- 真实仓库复核、用户试用和发布说明。

## 何时再次调整方向

满足以下任一条件时，必须重新评审，而不是继续堆功能：

- 真实仓库结果主要是低价值结构检查，用户没有行动意愿。
- AI 对照实验没有显示上下文、耗时、稳定性或可解释性收益。
- 安装成本高于用户愿意接受的程度。
- 用户最强需求明显转向 PR 自动检查、团队历史或其他入口。
- 维护多语言规则的成本超过两人团队能力。

调整方向不是失败。提前记录假设、证据和停止条件，才是把项目做成真实产品的必要流程。
